# 1회차 점검 기록 — B. 알람이 실제로 울리는 경로

- 시작: 2026-08-03
- 대상 빌드: `1448c6b` (Release)
- 기기: `32`(SM-A325N / RF9R3049REV, USB), `플립`(R5CR80EAMRE, USB), iOS는 `미니`(무선)
- **울림 모드: `진동만`으로 테스트** — 소리 없이 진행. 소리 경로는 12번에서 따로 확인
- 점검표: [pre-launch-checklist.md](pre-launch-checklist.md) B영역

## 진행 순서 (의존성 때문에 이 순서를 지킨다)

실제 시각에 울려야 확인되는 항목이라, **기다리는 시간이 겹치도록** 묶었다.
알람은 현재 시각 +2분으로 걸고, 걸어둔 뒤 해당 환경을 만들어 대기한다.

| # | 항목 | 준비 | 확인 |
|---|---|---|---|
| 1 | B-1 포그라운드 울림 | 앱 켠 채로 대기 | 울림 → "끄기" |
| 2 | B-1 백그라운드 울림 | 홈 버튼으로 내림 | 울림 → "5분 후" |
| 3 | B-1 스누즈 재울림 | 2번에서 이어짐 (5분 뒤) | 5분 뒤 재울림 → "끄기" |
| 4 | B-1 잠금화면 울림 | 화면 끄고 잠금 | 울림 → "끄기" |
| 5 | B-2 OFF한 알람 | 알람 걸고 스위치 OFF | **울리지 않아야 함** ← 가장 중요 |
| 6 | B-2 삭제한 알람 | 알람 걸고 삭제 | **울리지 않아야 함** |
| 7 | B-2 일부만 OFF | 2개 걸고 1개만 OFF | 나머지 1개는 정상 울림 |
| 8 | B-2 전부 OFF | 전부 OFF | 하나도 안 울림 (fail-open 아님) |
| 9 | B-3 재부팅 복구 | 알람 걸고 재부팅 | 재부팅 후에도 울림 |
| 10 | B-3 Direct Boot | 재부팅 후 잠금해제 전 | 잠금해제 전에도 울림 |
| 11 | B-3 Doze | 화면 끄고 방치 | 정확한 시각에 울림 |
| 12 | B-1 소리/진동 3종 | 각각 설정 | 실제 울릴 때 반영 (1~11은 `진동만`으로 진행, 여기서 소리 경로 확인) |
| 13 | B-4 주기 정확도 | 날짜 넘겨 확인 | 별도 회차로 분리 검토 |
| 14 | B-5 워치 | 워치 연결 시 | best-effort |

**5~8번(안 울려야 하는 케이스)이 이 회차의 핵심.** 경쟁 앱 최대 약점이 "알람 안 울림"이지만,
이 앱의 과거 버그는 반대로 "꺼도 울림"(Expo만 취소하고 AlarmManager를 빠뜨림) 쪽이었다.

## 발견한 문제

### 🔴 1. `test-alarm-suite.sh`의 AlarmManager 카운트가 항상 0 (수정 완료)

`dumpsys alarm`에서 `Pending alarm batches:` 헤더를 찾아 그 구간만 세는 구조였는데,
**`32`(SM-A325N / Android 13)에는 그 헤더가 아예 없다** — `RTC_WAKEUP #N:` 항목이 바로 나열된다.
헤더를 못 찾으니 구간 진입 자체가 안 돼 `COUNT`가 **항상 0**.

그 결과 `--all-off`의 **"알람 전부 끔 → 등록 0개 기대"가 실제 상태와 무관하게 늘 통과**했다.
이 프로젝트가 반복해서 겪은 버그가 정확히 "Expo만 취소하고 AlarmManager에 남아 꺼도 울림"인데,
그걸 잡으라고 만든 검사가 아무것도 검증하지 않고 있었다. 테스트가 녹색인데 의미가 없던 케이스.

**수정**: 헤더 진입 대신 이력/통계 섹션 시작 전까지를 대기 구간으로 보고,
이력 항목(`[tag=...`)과 실제 예약(`tag=...`)을 대괄호 유무로 구분해 센다.
수정 후 실제 예약 5건이 정확히 잡히고, OFF 후 0건도 정확히 잡힌다.

### 🟡 2. 스누즈("5분 후")가 기능 플래그로 꺼져 있음 — 확인 필요

`src/constants/index.ts:50`의 `SNOOZE_ENABLED = false`. 버그가 아니라 의도적 설정이고
주석도 달려 있다. 다만 점검표는 스누즈가 있다는 전제로 짜여 있었다.
**출시 시점에 스누즈를 계속 끈 채로 갈지 결정 필요** — 켤 거면 3번 항목을 되살려 테스트해야 한다.

### ⚠️ 3. Direct Boot(10번)는 검증되지 않았다 — 조건이 성립하지 않음

11:45 알람은 재부팅 후 정상 발화했지만, 그 시점 기기 상태가 `RUNNING_UNLOCKED`였다.
확인해보니 **`32`에는 보안 잠금(PIN/패턴/비밀번호)이 설정돼 있지 않다**
(`lockscreen.password_type=null`, `trustManaged=0`). `ro.crypto.type=file`로 FBE는 켜져 있지만
자격증명이 없으면 부팅 직후 CE 저장소가 바로 열려서, 재부팅 후 잠금해제 전 구간이 사실상 없다.

즉 이번에 확인한 건 **9번(부팅 후 재등록)까지**이고,
"잠금해제 전에도 울리는가"는 **여전히 미검증**이다. 정적 검사(`directBootAware`,
device-protected 저장소)는 통과했지만 실기기 확인은 안 된 상태.

**제대로 하려면**: `32`에 PIN을 설정한 뒤 → 알람 예약 → 재부팅 → **PIN을 입력하지 않은 채로**
발화 시각까지 대기. PIN 설정은 기기 소유자 결정이 필요하다.

### ✅ 4. 워치 대비 — 기기가 없어 실제 검증은 불가, 코드 레벨은 점검 완료

**이미 돼 있던 것**
- iOS 카테고리에 `customDismissAction: true` (전역 규칙 항목) — 워치의 "닫기"가 시스템 기본
  닫기여도 응답 리스너가 호출돼 재알림 취소가 누락되지 않는다
- 네이티브 알림: `CATEGORY_ALARM` / `PRIORITY_MAX` / `VISIBILITY_PUBLIC` / 채널 `IMPORTANCE_HIGH`,
  그리고 **`setLocalOnly` 없음**(있으면 워치로 아예 안 넘어간다)
- 액션이 `끄기` 1개 — `플립` 커버 화면 대응으로 줄인 것인데 워치 축소 뷰에도 유리
- 네이티브 `끄기` → `cancelReps()` 호출 확인. 워치에서 꺼도 반복 울림까지 정리된다
- 응답 리스너가 액션 종류를 안 가리고(탭/끄기/스와이프 닫기) 동일하게 Expo·네이티브 rep을 취소

**고친 것** — Android 알림 카테고리에만 `5분 후` 버튼이 남아 있었다. 인앱은 `SNOOZE_ENABLED=false`로
스누즈를 없앴는데 알림에만 남아, 액션 버튼이 크게 보이는 워치에서 눌릴 확률이 높았다. 게다가 그
스누즈 경로는 Expo 예약만 걸고 네이티브 AlarmManager는 안 걸어서 Doze 구간에서 안 울린다 —
앱에서 제거한 기능이 워치에서만, 그것도 가장 약한 경로로 살아나는 상태였다.
→ 액션 목록을 `SNOOZE_ENABLED`에 묶어 인앱·알림·워치가 항상 같은 버튼을 보이게 수정.

**한계**: Wear OS / 구형 Tizen / 저가 워치는 지원 수준이 제각각이라 100% 보장은 원래 불가능하다.
위 구성은 표준 Bluetooth 알림 브릿지 기준 best-effort다.

### ⏸ 5. iOS(미니) 빌드 중단 — 월 사용 한도 초과

`claude.ai/settings/usage`에서 한도 상향 필요. 그전까지 iOS 항목은 전부 미검증으로 남는다.
